Scope justification · opencode-google

Data access

Every Google scope this app requests, what it reaches, and why the narrower option does not work. If you are reading this to evaluate the app, this page plus lib/google_clients.py is the complete picture.

Architecture in one paragraph

opencode-google is a stdio MCP server. OpenCode launches it as a child process on the user's machine. It holds no listening socket, serves no HTTP endpoint, and contacts nothing except Google's own API hosts. There is no backend, no database, and no telemetry. The only persistent state is an OAuth refresh token stored locally at ~/.config/opencode/google/token.json with mode 0600.

Scopes requested

calendar.events — sensitive

Use: read events in a window, compute free slots inside working hours, create events, and update or delete an event after a preview is approved.

Why not narrower: calendar.readonly would cover reads but not creating or moving events, which is the primary use. calendar.events is already narrower than full calendar, which would add calendar-level settings and ACLs the app never touches. Deletes never happen on a first call: the Class C guard requires a second call carrying a one-time token bound to the exact payload.

gmail.readonly — restricted

Use: search the mailbox with standard Gmail syntax (for example is:unread newer_than:2d) and read a single thread the user named, with trimmed plain-text bodies.

Why not narrower: there is no scope that permits search and thread reading without granting read access to mail. gmail.metadata returns headers only and cannot answer “what did the client ask for”, which is the entire purpose.

Why not read-write: gmail.modify and gmail.compose were deliberately not requested. There is no code path in this server that can send, reply, label, archive, or draft mail. The tool list has no send tool at all — see the Class X section of SOP.md.

drive.file — recommended, non-restricted

Use: upload generated files, and list what the app itself created.

Why this is the narrow one: drive.file grants access only to files this app created or that the user explicitly opened with it. Google enforces that boundary. The app cannot see, read, or list the rest of your Drive even if it tried. On top of Google's boundary, every path is additionally checked against a single opencode folder in code, so a request outside that folder is refused before the API call is made.

documents — sensitive

Use: create a Doc inside the app folder, append text to it, and read a Doc's plain text back. Used for change requests and generated reports.

Why not narrower: documents.readonly cannot create the document. Creation is the feature.

spreadsheets — sensitive

Use: create a spreadsheet with a header row, read an A1 range, append rows, and overwrite a range after an approved preview.

Why not narrower: spreadsheets.readonly cannot create or append. Overwrites are Class C and preview current cell contents before anything is written.

tasks — sensitive

Use: list tasks, create a task with a due date, and mark a task complete. Completion is trivially reversible and is Class R.

Why not narrower: tasks.readonly cannot create or complete, which removes the entire reason to connect Tasks.

contacts.readonly — sensitive

Use: resolve a person's email address by name so an event's attendee list is correct.

Why read-only: the app never creates or edits contacts. The scope is already the narrowest available for lookup.

Where the data goes

Three destinations, and no others:

  • Google's API endpoints, over TLS, from the user's own machine.
  • The local OpenCode session, in memory, for the duration of the request.
  • Nowhere else. No analytics, no logging service, no third-party backend.

One honest caveat: tool results are returned into the OpenCode conversation, which is processed by whichever model provider the user configured. That is the same channel as anything else the user types or reads. Choosing the provider is the user's decision, made outside this app.

Human access

No human reads your Google data through this project, because the project has no copy of it. Nobody operating this app can retrieve your email, calendar, or files. There is no admin panel, no support tool, and no log to inspect.

Retention and deletion

  • The server persists no Google content beyond the refresh token.
  • Delete ~/.config/opencode/google/token.json to remove the token from disk.
  • Revoke at myaccount.google.com/permissions to end access immediately.
  • Files the app created remain in your Drive under a folder named opencode; delete or move them in the Drive UI.
Verify it yourself. The repository is public. lib/google_clients.py lists the scopes; server.py lists all 22 tools; lib/confirm.py implements the preview-token guard; SOP.md states the rules the code enforces. Tests run without network access: .venv/bin/python tests/test_confirm_guard.py.

Limited Use compliance

opencode-google's use of information received from Google APIs adheres to the Google API Services User Data Policy, including the Limited Use requirements. See the privacy policy for the full disclosure.
